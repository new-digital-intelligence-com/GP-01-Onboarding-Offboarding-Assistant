Architecture note

AI Employees as Artifacts

How one skill, a published HTML page, and a set of connectors add up to something that does real work — and where each piece actually runs.

This is a pattern, not a product. Anywhere it says the skill, substitute yours; anywhere it says a connector, substitute whichever ones you need. One worked example runs alongside it in the margin notes, but nothing here depends on that example.

01One skill, more than one way in

The skill is a Markdown file. It holds the rules — what to do, in what order, what is verified, what must never happen. It contains no code and calls nothing.

That file is the only implementation. Every surface reaches the same file, and none of them re-states a rule in code. The moment a rule exists twice, the copies drift and every fix has to be made in both places.

02Build is not publish

Two separate actions, and confusing them causes most of the early mistakes.

Your source page has a hole in it — a placeholder word that means nothing to anyone. A build script reads your skill files and does a find-and-replace, writing a second file with the hole filled. That second file is what gets published.

The rule

Edit the source. Publish the built file. Never edit the built file — the next build overwrites it.

03What is actually inside the page

Three things, and none of them is intelligence.

The capabilities, and which one thinks

Each one is requested separately and can come back empty — not granted, not available on that plan, not served in that view. So every one of them is checked before use, and the page is designed to still make sense without any given one.

04Where the thinking happens

This is the part that resists intuition: the model is not in the page.

Asking it something is a message over the internet, exactly like a chat app. Your phone does not contain the person you are texting. The page does not contain Claude.

So the skill is not read by Claude in any file sense. The page sends it as part of the message, every time. It is the same as pasting it into a chat window, just done in code.

05One run, start to finish

A run is a loop. The page opens it with one long message and then plays messenger until the model says it is finished.

Why the page gives the model functions, not knowledge

The functions a page offers should be plumbing, not procedure. A single pass-through that forwards {connector, tool, arguments} keeps every rule about what to call and when in the skill, where it can be read and corrected. The moment the page contains a function called createTheAccount(), the logic exists twice.

Useful functions to offer, in rough order of value:

  • Call a connector — one pass-through, validated against the allowlist.
  • List what is reachable — so the model uses real names instead of guessing.
  • Log an event — so the visible record comes from structured calls, not from parsing prose.
  • Remember a fact — anything needed later that cannot be cheaply looked up again.
  • Finish — an explicit end, so "it stopped" and "it finished" are different things.

06Who holds the credentials

Nobody can put a secret in a published page — it is delivered to the browser, and anyone who opens it can read every line. So the page holds no token at all. It names a connector, and the credential is attached on Claude's side, per viewer.

The design decision this forces

If every person needs their own connector, each one behaves slightly differently and each needs setting up. If an administrator publishes one connector for the whole organisation, every run is identical and nobody sets anything up — but then anyone who can open the page can do everything it does. Pick deliberately; there is no third option.

07The four limits you will hit

None of these are bugs, and all four bite in the first week.

LimitWhat happensWhat to do
Tool rounds One request gets a bounded number of tool calls. A long job runs out partway and the model is told tools are off. Split a job into parts. When one ends unfinished, send a fresh request carrying what already happened and an instruction not to repeat it.
Prompt size There is a cap on how much text one request may carry. A long skill plus a growing log will reach it. Check the size at build time and fail the build, not the run. Keep the carried-forward log short.
The tab There is no server. Closing the page kills the job mid-step. Anything already done stays done. Write progress to the database as it happens, never only at the end. Warn before unload.
No network The page cannot call any outside address directly. Requests are blocked. Everything external goes through a connector — including anything of your own, wrapped as a server and added as one.

Two failure modes worth designing for early

State does not survive a part boundary. Anything the model generated and did not write down is gone when the next part begins. If it generated a credential in part one and cannot recall it in part two, it will generate another — and may apply it again. Make such values stable: generate once, return the same value on every later request, and carry it forward explicitly.

Repeated lookups are expensive in the only currency that matters. A catalogue that cannot change during a job should be fetched once and served from memory afterwards. Each repeat costs a tool round, and tool rounds are what run out.

08The worked example

The pattern above was built out against one real case: an onboarding and offboarding assistant that creates and suspends staff accounts, sends their first emails, posts a welcome, and writes an audit row for every item.

In the patternIn that case
The skill~47 KB of rules: what is verified, what is handed to a human, what is impossible and why
The connectorOne broker fronting the mail, chat, directory and spreadsheet systems
The pass-through{connector, tool, arguments} — no system-specific shape in the page
Parts per job4, after the round-waste was fixed; 6 and unfinished before
The databaseRun history and a repeat-run guard

The numbers are not the point. The point is that every one of them was discovered by running it for real, and that each discovery changed the skill rather than the page — which is the whole reason the skill is kept as the only implementation.

What transfers to any other case

  1. Write the rules as prose, in one file, and keep them there.
  2. Give the model plumbing, not procedure.
  3. Assume every job spans several parts, and design the hand-off before you need it.
  4. Put every fact you verify back into the skill, with the date and what you observed.
  5. Decide who holds the connector before you decide who gets the link.
An architecture note. The mechanisms described here are properties of the artifact runtime and of the connector model, not of any one assistant built on them.
